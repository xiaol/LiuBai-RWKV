# Review: 2026-10-25

Scope: the current working tree, including uncommitted VAE v3/v4 and cursor-LM work; current logs and saved evaluation JSON. Historical YuE2 code was inspected selectively. This is a review, not a training run or a source-code fix.

The project has a promising codec and a sensible research direction, but lyric-controlled generation remains unproven. Fix training/evaluation correctness before another large architecture change or a 2.9B run. The evidence does not establish that the VAE alone caused the failed generation experiments.

## Findings, ordered by priority

### P1: manually synchronized modules do not share their initial parameters

`vae/train.py:59` uses a different initialization seed per rank. Only G is wrapped in DDP (`:89`); D, CTC, prior and alignment heads only receive averaged gradients (`:91`). Gradient averaging does not synchronize different starting weights. Fresh v3/v4 alignment heads are neither loaded in the `--init` branch nor broadcast. Every rank therefore trains a different feature mapping while averaging its parameter gradients with the others.

A CPU reproduction using the actual AlignHead and optimizer retained exactly the same maximum inter-rank weight difference, 0.35105276, after an averaged-gradient update. The same problem affects fresh D/CTC/prior on a from-scratch distributed run; loading a common checkpoint synchronizes those modules.

Scope caveat: v3's current log starts from v2, while v4's current log resumes at step 7500. Loading that common v4 checkpoint also loads heads and optimizer states, synchronizing the later segment. Do not label the entire 60k v4 run desynchronized. Its initial segment and the v3 experiment remain suspect under the current initialization path.

Fix: broadcast all manually synchronized module parameters and buffers after initialization/loading, before training. Test equality across ranks before and after an optimizer step. Preserve existing checkpoints, then run a controlled short comparison.

### P1: the continuation prompt contains information from future reference audio

`vae/eval_cursor_lm.py:93` encodes the complete 24-second reference, then `:103` extracts its initial latent blocks as the supposedly 4-second real prompt. `vae/model.py:91` runs bidirectional encoder blocks. V4 additionally uses bidirectional MERT and temporal normalization. The prompt can therefore contain information from the held-out continuation.

A small CPU VAE reproduction changed only future audio and changed earlier prompt latents (maximum difference 0.00698). This is a codec/evaluation boundary issue, not a causal-mask failure in CursorLM: a separate causal-prefix invariance check passed.

Fix: independently encode only the available prompt, with explicit bounded lookahead if necessary. Compare isolated-prompt encoding with whole-reference encoding. Evaluate codec chunk/context consistency as well: the VAE trains on 8-second crops, the LM consumes 24-second encodings, and round trips use whole songs.

### P1: CTC targets omit audible partial lyrics at the beginning of a crop

`vae/data.py:75` excludes any line starting before the crop, but the CTC input in `vae/train.py:116` starts at frame zero. Only the ending frame is truncated. Therefore the loss penalizes transcription of the previous line's audible tail, or encourages incorrect alignment of the next complete line to that tail. This also affects latent probes and the decoded-audio CTC judge using these targets.

Reproduction: a crop covering [2,10] seconds with lines [0,4] “old line” and [4,8] “new line” is marked valid with target “new line”, although its CTC window includes two seconds of “old line”.

Fix: provide valid start/end frame intervals and crop logits accordingly, or reject crops with partial leading vocals. Verify intervals against actual vocal timing rather than assuming LRC intervals precisely mark singing.

### P1: evaluation can silently pair a new LM with the wrong VAE

`vae/eval_cursor_lm.py:33` defaults to VAE v2 and loads it before reading the LM checkpoint. The training VAE path is already stored in `sd['args']['vae']`, but is ignored. A v4-trained LM evaluated with the documented minimal command would use v4 latent statistics with the v2 codec. Shapes match, so this can silently produce invalid audio rather than an error.

Fix: resolve the codec from the LM checkpoint by default; require an explicit, checked override. Store a codec fingerprint, latent-normalization metadata and manifest identity in every run.

### P2: saved architecture comparisons use different evaluation crops

The 24 `own` reference texts in `out/clm_eval/cursor1_25k/eval.json` and `prefix1_25k/eval.json` have **zero pairwise matches**, despite both recording seed 0. Their original-audio CERs are 0.489 and 0.408 respectively. The existing numbers do not support a paired claim that cursor beats prefix.

The current audio evaluator explicitly seeds Python random, which may address the historical sampling issue. However, `Crops.__iter__` mixes global random state into its nominal seed (`vae/data.py:66`), and `train_cursor_lm.py` does not seed Python random before constructing validation crops. A seed in config alone is insufficient evidence that the cohorts match.

Fix: persist a fixed evaluation manifest containing song identity, crop offsets, exact references and swap assignments, and load it across experiments. Use paired generation noise streams; the current shared advancing generator also makes outputs depend on condition ordering.

### P2: ASR caching and missing outputs can invalidate round-trip scores

`tools/yue2_roundtrip_eval.py:68` caches transcripts by relative filename only. Rendering another checkpoint to the same tag, changing audio, or changing ASR language/model reuses the old transcript. At `:86`, an empty hypothesis becomes NaN and is later excluded from the mean; for a nonempty reference, empty output should be a deletion error of 1.0.

No empty transcripts were present in the inspected cache, so the latter is a confirmed code defect, not a demonstrated cause of the current v4 score. No claim is made that the new v4-60k tag was scored from a stale transcript.

Fix: key by audio content and ASR configuration; report failures explicitly and score empty hypotheses correctly. Save immutable per-run score files rather than repeatedly overwriting the shared eval.json.

### P2: generation replays all history and does not carry RWKV state

`vae/eval_cursor_lm.py:65` invokes `M.hidden(z[:, :i+1], ...)` at every generated block; `vae/cursor_lm.py:92` recomputes every recurrent layer over that prefix. Backbone work grows quadratically with song duration. The design's constant-state inference advantage is not implemented in this path.

Fix after the correctness gates: add recurrent step/state APIs, carry TimeMix matrix and token-shift states, and check parity against full-prefix inference. The bidirectional decoder separately needs an explicit bounded-window streaming design.

## What to do next

1. Fix DDP initialization, CTC intervals, checkpoint/codec binding and evaluation provenance. Add focused regressions for these behaviors. Freeze a development cohort plus a genuinely untouched song-level test cohort; the repeatedly used gate20 should be treated as development data.
2. Finish the already-running v4 probe. Compare v2/v4 on the same crop lengths and on independent intelligibility and bandwidth-matched quality measures. Keep v4 as a candidate, not an automatic replacement.
3. Run a small lyric-control diagnostic before another long run: overfit a small clean vocal subset, then compare **oracle cursor timing**, **predicted cursor timing**, **swapped lyrics** and **null lyrics** with identical models, data budgets and prompts. Include a direct MERT-conditioned diagnostic to establish whether the semantic representation can drive the decoder. This separates alignment/cursor failure, representation failure and flow-model/exposure failure.
4. Only scale if the small model can sing the supplied words: a concrete starting gate is held-out own CER below 0.60 and a consistent paired improvement over null/swapped lyrics, with original and VAE ceilings reported on those exact crops. Run multiple seeds and inspect audio, not just teacher-forced flow gaps. If oracle timing succeeds but predicted timing fails, fix the advance model; if oracle timing fails too, scaling the cursor LM is premature.
5. After lyric control works, implement stateful inference, caption/style conditioning and long-song structure, then test 48 kHz and larger models. The current cursor pilot uses a real-audio style prompt; it is not yet the full caption-plus-lyrics product.
6. Update README/PLAN to point to the actual continuous-latent stack, document the v4 design and dependency setup, and commit the currently untracked core files with experiment provenance. The README currently describes September's YuE2 pipeline as current.

The claim “both generators failed, therefore the VAE is the problem” is too strong. Those experiments share crop targets, alignment and evaluation machinery, and their timing/generalization assumptions have not been isolated. V4's improved reconstruction and probe readings justify a controlled experiment, not another architecture jump or a Suno-level performance claim.
